## 2. 形式

- Markdown で作成し、`docs/` 配下に置く。
- 図は Mermaid で記述する（GitHub上でそのまま表示されるため）。
- 一覧類は Markdown の表で記述する。
- 各文書の冒頭に改訂履歴（版、日付、内容、作成者）を置く。

## 4. 要件定義書の構成

| ファイル | 記載内容 |
|---|---|
| 01_概要.md | 想定顧客、背景、目的、狙い、スコープ（対象／対象外） |
| 02_業務要件.md | 業務機能構成表、業務フロー図（As-Is／To-Be）、課題一覧 |
| 03_機能要件.md | システム方式（AWS構成の概要）、機能一覧、画面一覧、画面遷移図、帳票一覧、バッチ一覧、外部システム関連図、外部インターフェース一覧、概念ER図、テーブル一覧 |
| 04_非機能要件.md | 可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境・エコロジー |
| 05_前提・制約.md | 前提条件、制約条件、未決事項一覧 |
| 99_用語集.md | 用語定義 |

非機能要件の6分類は IPA「非機能要求グレード」に基づく。

### 作成しないもの

| 成果物 | 理由 |
|---|---|
| ハードウェア構成図 | クラウド構成のため、システム方式（AWS構成の概要）で代替する |
| 帳票レイアウト | 帳票一覧のみとする |
| 業務処理定義（詳細） | 業務フロー図で代替する |
| 外部インターフェース定義書 | 基本設計で作成する |

## 5. ID規則

| 対象 | 形式 | 例 |
|---|---|---|
| 業務要件 | `BR-nnn` | BR-001 |
| 機能要件 | `F-nnn` | F-001 |
| 非機能要件 | `NF-nnn` | NF-001 |
| 未決事項 | `Q-nnn` | Q-001 |

- 一度付与したIDは変更・再利用しない。削除した要件は欠番とする。
- 設計書・テスト仕様書では、対応する要件IDを記載して追跡できるようにする（トレーサビリティ）。
- 画面・バッチ・帳票・外部インターフェースのIDは、機能要件の作成時に決める。

※ 接頭辞は本プロジェクト独自の取り決めであり、業界標準ではない。

## 6. フェーズ表記

各機能要件に、実装するフェーズ（1〜5）を記載する。要件は全範囲で記述し、実装範囲はこの表記で区別する。

## 7. 分量の目安

ポートフォリオ用のため、実際の現場の文書よりも簡潔にする。機能要件は20〜30件程度を目安とする。

## 8. 要件定義の完了基準

- すべての機能要件にIDとフェーズが付いている
- 業務フローの各処理が、機能一覧のIDと対応している
- 未決事項がすべて決定済み、または保留理由が記載されている
