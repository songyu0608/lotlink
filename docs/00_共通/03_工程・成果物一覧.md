## 1. 方針

- 上流工程（要件定義・基本設計）は文書を成果物として残す。
- 下流工程（開発・テスト）はコードとCIの実行結果を主な成果物とし、文書は代表例に絞る。
- すべての処理について詳細設計書やテスト仕様書を作ることはしない。

## 2. 工程別の成果物と粒度

| 工程 | 成果物 | 粒度 |
|---|---|---|
| 要件定義 | 要件定義書一式（`02_ドキュメント規約.md` の4章を参照） | 全フェーズを対象 |
| 基本設計 | システム構成図（AWS）、ER図、テーブル定義書、API仕様書、画面設計（主要画面）、バッチ設計（概要）、外部インターフェース定義書 | 全フェーズを対象（簡潔に） |
| 詳細設計 | 処理フロー、ロジックの説明 | 重要な処理のみ（在庫引当、Amazon注文CSV取込、日次集計） |
| 開発 | ソースコード、プルリクエスト、CI設定 | フェーズ順に実装 |
| 単体テスト（UT） | テストコード（pytest）、CIの実行結果、単体テスト仕様書 | テストコードは全機能。仕様書は代表1機能のみ |
| 結合テスト（IT） | API〜DBを通したテストコード、結合テストシナリオ一覧 | 主要シナリオ |
| 総合テスト（ST） | 業務シナリオテスト（受注 → 引当 → 出荷）、非機能要件の確認結果 | 最小限（業務シナリオ1本） |

## 3. 要件定義のサブステップ

| ステップ | 内容 | 成果物 |
|---|---|---|
| 1 | 前提設定 | 概要（背景・目的・狙い） |
| 2 | As-Is整理 | 業務フロー図（As-Is）、課題一覧 |
| 3 | To-Be／スコープ | 業務機能構成表、業務フロー図（To-Be）、スコープ定義 |
| 4a | システム方式・機能 | システム方式（AWS構成の概要）、機能一覧 |
| 4b | 画面 | 画面一覧、画面遷移図 |
| 4c | バッチ・帳票・外部連携 | バッチ一覧、帳票一覧、外部システム関連図、外部インターフェース一覧 |
| 4d | データ | 概念ER図、テーブル一覧 |
| 5 | 非機能要件 | 非機能要件一覧 |
| 6 | 前提・制約／未決事項 | 前提条件、制約条件、未決事項一覧 |
| 7 | 統合・レビュー | 要件定義書 v1.0、用語集 |

各ステップは「初稿の提示 → レビュー・修正 → 確定」の順で進め、確定後に次のステップへ進む。
